WHY THIS FILE EXISTS

The artwork lives in the `product_images` table (migration 0012), which is bytes in
Postgres — so it is not in this repository and a `git clone` does not bring it.
The generated files themselves arrived with names like

    ChatGPT Image Aug 18, 2026, 08_40_06 AM (7).png

which say nothing about which drink is inside. Every mapping below was established
by LOOKING at each image; nothing about the filenames or their order encodes it.
That identification is the part worth writing down: without it, restoring the
artwork means redoing the visual matching from scratch.

THREE THINGS THAT MADE THE FILENAMES UNTRUSTWORTHY

  1. The download timestamps are NOT batch order. The 08_39_42 group is prompt
     batch 2; the 08_39_51 group is batch 1.
  2. Order WITHIN a group is not prompt order either. In the 08_39_51 group,
     image (6) is the espresso macchiato and image (2) is the Spanish latte.
  3. The 08_40_17 group is a byte-for-byte duplicate of 08_40_06 — the same batch
     downloaded twice, not a fifth batch.

--------------------------------------------------------------------------------
HOW THESE WERE PROCESSED
--------------------------------------------------------------------------------

Sources were 1254x1254 (loose) and 1024x1024 (zips), all RGBA with real
transparency — verified by decoding the alpha channel, not by eye: transparent
corners and 49-90% fully transparent pixels on every file.

Each was then put through the SAME pipeline src/imageNormalize.js applies in the
browser, because the server accepts nothing else (exactly 512x512 PNG):

    trim to the alpha bounding box, ignoring alpha < 32 as halo
    scale the subject to 440px on its longest side
    centre it on a 512x512 fully transparent canvas
    export PNG

then PUT to /api/product-images/:id as base64. Result: 43 rows, ~12MB total in
Postgres, every stored file re-verified as a valid 512x512 PNG with its
transparency intact.

--------------------------------------------------------------------------------
CATEGORY TILES — promoted from product artwork, not generated separately
--------------------------------------------------------------------------------

The six category tiles were showing coloured letter badges, because the bundled
artwork in src/assets/categories/ is the LIQUOR set and none of its names match this
shop's categories. Rather than generate six more images, one representative drink per
category was promoted into category_images (migration 0009):

  hot coffee   <- KC-HC-07  Cafe Latte        (rosetta reads instantly as hot coffee)
  cold coffee  <- KC-CC-01  Iced Latte        (layered, obviously cold)
  tea & herbs  <- KC-TH-06  Moroccan Tea      (green; nothing else in the set is)
  hot kan      <- KC-HK-01  Hot Chocolate
  cold kan     <- KC-CK-04  Fresh Juice       (orange; carries at tile size)
  special      <- KC-SP-07  Affogato

Chosen for instant recognition AND for colour spread, because unlike the product
tiles all six of these are seen at once.

TWO THINGS TO KNOW

The bytes are a COPY, not a reference. Replacing a product's picture does not update
the category tile that was promoted from it — re-promote it, or upload the category
image directly at Settings -> Categories, which is the supported path and overwrites
whatever is there.

The keys are the category name lowercased and trimmed ('tea & herbs'), which is what
categoryImage() on the client resolves by. If a category is ever renamed, its tile
silently falls back to the letter badge until the image is re-keyed.

These were written straight into category_images rather than through
PUT /api/category-images/:cat. That is not a way around the upload validator: the same
bytes already passed it as 512x512 PNGs with alpha when they went in as product images.
